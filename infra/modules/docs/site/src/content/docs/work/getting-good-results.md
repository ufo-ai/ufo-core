A good request states an outcome, not a sequence of clicks.

> Review support tickets from the last 30 days. Group repeated onboarding problems, count affected
> customers, link representative tickets, and draft three product actions. Do not reply to tickets.

## Include five facts

1. **Outcome:** what must exist when the work is complete.
2. **Scope:** systems, repositories, accounts, time ranges, and environments.
3. **Constraints:** what must not change and which rules apply.
4. **Proof:** tests, source links, queries, screenshots, or checks that establish the result.
5. **Delivery:** conversation, pull request, file, site, or connected destination.

## State authority

Use direct boundaries such as “do not send,” “do not merge,” or “production is read-only.” If the
agent may publish or change external state, name the exact system and action.

## Correct the course

Continue in the same conversation when new context belongs to the same result. State what is wrong,
provide the missing fact, and name the revised outcome. Start a new conversation for unrelated work.

## Ask for evidence

Request a source for factual claims and a rendered check for visual output. Ask the agent to state
uncertainty instead of filling a missing fact with an assumption.
