# ufo harness handbook

A navigable, bottom-up reference to the ufo harness: every Python file read and
described, grouped into an ordered lifecycle of **stages**, narrated from
per-function leaves up to a system overview. Generated by the
[Harness Handbook](https://github.com/Ruhan-Wang/Harness_Handbook) pipeline
(model `gpt-5.5`) — read it, don't hand-edit it.

> **Generated, not authoritative.** These pages are written by an LLM from the
> source and are refreshed wholesale every 48h; treat them as a map, and verify
> any specific claim (a type, signature, mechanism, or filename) against the code
> before relying on it. They are excluded from AI code review for this reason.

## Read it

- **[overview.md](overview.md)** — the whole system in a few paragraphs. Start here.
- **[index.md](index.md)** — every stage, its file count, and one paragraph on its role. The routing table, and the authoritative current stage ordering.
- **[register.md](register.md)** — cross-stage state (config stack, credentials, session/turn state, tool catalog, sandbox policy, persistence handles) and which stages touch each.
- **`stage-*.md`** — one page per stage, ordered by the call graph (entry points first, callers before callees). Sub-stages use dotted ids. Each page carries per-file and per-function detail: purpose, data flow, and call relations.

The spine follows the harness lifecycle: process startup → database migrations →
extension/pack loading → connector setup → workspace provisioning → sandbox prep
→ surface ingress → job scheduling → the turn-execution loop (model invocation,
tool calls, transcript/memory, egress) → data sync → periodic maintenance →
onboarding → crosscutting concerns (config, protocols, persistence, telemetry).
See `index.md` for the exact stage ids and ordering of this revision.

## Scope

- **Included:** all Python application source — `core/`, `extensions/`, `control/`, `sandbox/`, `packs/` (392 files, 63 stage pages).
- **Excluded:** tests, and the React web-surface UI (`*.tsx`/`*.ts`). The generator's TypeScript adapter is incompatible with the current `tree-sitter` binding; the harness itself is Python, so this omits UI rendering only, not harness logic.
