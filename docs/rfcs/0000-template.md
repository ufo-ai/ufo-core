# <Title>

> One paragraph: what this proposes and why it matters now. Link the spec section or code it changes.

Status values: `proposed` (open, under discussion) · `accepted` (agreed, not yet built) ·
`implemented` (built and merged) · `rejected` · `withdrawn`. A rejected/withdrawn RFC stays in this
folder with its status set — nothing is deleted, so the reasoning survives.

## Current state

What exists today, cited to `file:line`. Be precise about the gap.

## Proposal

The design. Prefer a table to prose; one concrete example, not three. Name the seams it touches and
whether any is new. Keep every hard-to-vary decision; cut the words around it.

## Doctrine fit / implications

How it sits with `spec.md` (core/extension boundary, one-shape, fail-loud, both-ends). What stays out
of core. What changes for the reader.

## Alternatives

The options not taken, and why.

## Open decisions

The forks that are genuinely the owner's to make.
